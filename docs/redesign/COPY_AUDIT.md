### 5-2. 슬롯 요약 ("스킬 10 · 문양") 대체안

**현재 값의 출처**: 슬롯 객체 `{ id, skill: 10, rune: true, rotation: '' }` (`app.js:893, 928, 1368, 1422`)의 `skill`(구 전역 스킬 레벨, 기본 10)과 `rune`(도장, 기본 true). 기본 편성은 5명 모두 같은 값이라 **슬롯 5개가 똑같은 글자를 반복 = 정보량 0**. 게다가 "문양"은 게임에 없는 말.

**실제 결과를 바꾸는 슬롯 필드** (`app.js:314~391`, `3700~3780`, `dashboard/spec.js`):

| 필드 | 의미 (공식어) | 기본값 | 결과 영향 (spec.js 공식 기준) |
|---|---|---|---|
| `spec.evo` | 스타 (0~5) | 5 | 가장 큼 — 배율 `1 + 0.10·evo(evo+1)/2` (★5 ×2.5, ★3 ×1.6) + 패시브 3~5·도장 잠금 |
| `spec.level` | 레벨 (1~60) | 60 | 큼 — `1.05^(level−1)` (Lv50은 Lv60 대비 −39%) |
| `rune` (+ `spec.evo≥3`) | 도장 잠금해제 | true | 큼 — 필살기가 도장 필살기로 바뀌고 도장 패시브 효과가 생김 |
| `spec.compat` | 적합도 (0~5) | 5 | 중간 — `1 + compat × 0.04(XXL)/0.03(XL)` (0이면 −17%) |
| `spec.lv{slot}` | 스킬 레벨 (슬롯별 1~10) | 10 | 캐릭터마다 다름 |
| `sealOn/sealAtk/sealHp` | 도장 제련 (ATK/HP 가산) | 꺼짐 | 작음~중간 |
| `spec.pevo` | 진화 단계 | 0 | 작음 — `+0.02 × pevo` |
| `plan / ult / usePlan` | 턴별 행동 계획 · 필살기 사용 방식 | 자동 | 큼 (행동 순서) — 단 슬롯보다 "행동 순서" 영역 소관 |

**제안**
1. 기본(최대 육성, `spec.on=false`, 도장 켜짐)일 때 슬롯 요약에는 **포지션만** 표시: `● 방해` (점 = 속성색). 5개 슬롯이 서로 다른 정보를 보여주고, 팀 포지션 구성이 한눈에 보인다.
2. 기본과 다를 때만 **차이 칩**을 영향 큰 순서로 최대 2개 추가, 나머지는 "+N":
   `★3` → `Lv50` → `도장 없음` → `적합도 2` → `스킬 조정` → `제련 +600`
   예: `● 전사 · ★3 · Lv50`, `● 보조 · 도장 없음`
3. 팀 전원이 최대 육성이면 슬롯마다 반복하지 않고 편성 패널 머리에 한 줄: "전원 최대 육성 (Lv60 · ★5 · 적합도 5 · 스킬 Lv10 · 도장 잠금해제)".
4. "스킬 10" 표기는 폐기 — `skill` 전역 필드는 스펙이 켜지면 `spec.lv`로 대체되는 구 필드라 사용자가 판단에 쓰지 않음(추정: 구 공유코드 호환용).
5. 라이브의 `★N` 배지(`app.js:1508`, 스펙 켠 슬롯)는 2번 규칙에 흡수. 툴팁 "캐릭터 스펙 설정 사용 중 — 스타 N · LvN · 육성도 N" → "육성 설정 사용 — N스타 · Lv.N · 적합도 N".

## 7. i18n 영향

**구조**: 번역이 두 방식으로 섞여 있음.
- `i18n.js` — 렌더된 DOM의 **한국어 원문 전체를 키로** 매칭(EXACT 473 · SUB 174 · PAT 22, 언어 4개 en/zh/zhs/ja × 각 약 470). 한국어를 한 글자만 바꿔도 4개 언어 매칭이 모두 끊기고 영어 등이 한국어로 노출됨.
- `app.js` 인라인 사전 — `ALTAR_T` 등 `{kr, en, zh, zhs, ja}`를 **ID 키**로 보유(약 123항목). 이쪽은 `kr` 값만 바꿔도 다른 언어가 깨지지 않음.

**변경 규모 추정**
| 범위 | 수 |
|---|---|
| 용어 규칙(§2)에 걸리는 EXACT+SUB 키 (중복 제거) | **151 / 647 (23%)** |
| 해요체·이모지 정리로 추가로 바뀌는 EXACT/PAT 키 | 약 40 (일부 위와 중복) |
| 합계 — 키를 새로 만들어야 하는 i18n.js 항목 | **약 180키 × 4개 언어 = 약 720항목** |
| 그중 번역문 자체도 바꿔야 하는 것 (의미가 바뀜) | 약 60키 × 4 = 240: `Rune → Sigil`(SH 영문 표기, 약 12), `Growth → Compatibility`/ja `適合度`(약 10), "길드전" 삭제(zh `公會戰密室` → `公會密室`, 3), 별의 제단 설명 재작성(4), 인라인 사전의 `ultimate` → `EX Skill` 통일(약 30) |
| 나머지 약 120키 | 한국어 키만 바뀌고 번역문은 그대로 이전 (예: "베리어"→"배리어" = `Barrier` 유지, "치유"→"치료" = `Healer` 유지) |
| app.js 인라인 사전 | `kr` 약 60항목 수정, 다른 언어는 의미 변경분만 |
| 백엔드 | "치유"(sim_api.py·boss_api.py·boss_sim) → "치료" 동시 변경 필수 (i18n 키 "치유"·"아군 치유"·"치유형" 3개와 한 쌍) |
| 참고 | app.js 한국어 리터럴 433개 중 239개는 EXACT 키와 정확히 일치하지 않음 — 상당수는 PAT·SUB·인라인 사전으로 처리되지만, 일부는 현재도 번역 누락일 가능성(미검증) |

**키를 한국어 원문 대신 ID로 바꾸는 방안**
- 장점: 한국어 문구를 고쳐도 4개 언어가 깨지지 않고, 문구 교정과 번역을 분리할 수 있음. app.js 인라인 사전(`ALTAR_T` 방식)이 이미 이 구조라 선례가 있음.
- 단점: 현재는 "DOM 텍스트를 사후에 덮어쓰는 볼트온" 구조라, ID로 가려면 app.js·index.html에서 문자열을 내보내는 곳 약 700곳을 `t('id')` 호출로 바꿔야 함(SUB·PAT의 부분 치환 로직도 재설계).
- 권장: 이번 문구 교정은 **v2(`dashboard_v2/`)를 새로 쓰는 김에 ID 키로 시작**하고, 라이브 v1은 §2의 A-1·A-3·A-8·A-11·F-1~F-4 같은 사실·공식어 오류만 키 이전(한국어 키 교체 + 기존 번역문 이동)으로 최소 수정.
